# 计划 4 验证记录：校验模型的校准

2026-10-01。对应 `2026-10-01-taskgen-v2-plan-4.md` 的 Task 6、7，是设计 §5 阶段 F 的完成证据。这里只列计数和 id，不摘录题目内容。新出的候选、样本、投票、标注都在 `results/plan4/`，只在本地，不进 git。

## 1. 这次改了什么

计划 4 按设计 §4.6、D4、D5 改了校验，并量了 `deepseek-v4.1-flash`（ollama.com）的准确率：
- **模型调用。** 返回 `finish_reason`；HTTP 200 却没有消息体时重试；出题时回答在 max_tokens 处被截断，记 `Truncated`，可重做。
- **校验。**
  - `TASKGEN_VERIFY_MODELS` 配几个模型各投几票，每个模型 Yes 多于 No 才过，全部模型过才过。
  - 每条题附档案的数据怪异点。
  - 思考用光 token、没给结论的票不算票，下次运行重投。
  - 结论行认得更宽。
  - 任务的 meta 按模型记每一票。
- **流水线。** 检查 → 预封顶（每模板 ≤25、每库 ≤900）→ 校验 → 终封顶。
- **校准工具。** 五种改坏（`corrupt.py`）；比较两份 SQL 留下的库（`check.final_state`）；`scripts/verify_calibrate.py`（组装样本、投票、标注表、复核页、报告）。

**被拒的 5 条 DySQL 金标准**：dysql:bowling:87、bowling:98、entertainment:117、retail:87、retail_world:25。按校验模型的理由归类：
- 3 条是删除后留下孤儿行，外键没一起处理：bowling:87、bowling:98、retail:87；
- 1 条是新行的必填值没说：entertainment:117；
- 1 条是"加 10 件"既可以理解为新增一行，也可以理解为改数量：retail_world:25。

这些都是 DySQL 金标准可以商榷的地方，不全是误杀。

## 7. 结论

- **规则：每条 1 票，Yes 就过**（`calibrate.choose_rule` 选出；`verify.DEFAULT_VOTES = 1`）。§3 的两个目标都达到：正样本通过 98.3% ≥95%，负样本被拒 100% ≥80%；标注集好题通过 98.1%。
- **D4 的第二个模型不加。** 一个模型、一票就达标。
- **负样本全部被拒，要打个折扣。** 程序改坏的地方往往让 SQL 和 instruction 明显对不上，比如换了值、少了一条写语句，真实的坏题更隐蔽。标注集里唯一的坏题（副本 ID 的顺序）就被放过了。这类坏题要靠检查规则或出题 prompt 来防，见第 8 节。
- **同系偏差**（设计 D5）。DySQL 金标准被 DeepSeek-R1 筛过，正样本 98.3% 可能偏高；新一批 v2 好题通过 98.1%，和它接近。

## 8. 给下一份计划的输入

- **被放过的坏题类别：** archive 一次复制多行时，副本的自增 ID 取决于插入顺序。两个办法：
  - 检查：同一张表有两条以上 `INSERT … SELECT`，且复制的行按 rowid 排序和按语句顺序不同时，拒绝。
  - 出题 prompt：复制多行时要求写成一条 `INSERT … SELECT … WHERE key IN (…)`。
- **误杀：** 好题被拒约 2%，多是"按名字或条件找行，校验模型担心不唯一"。可以考虑给校验模型看 SQL 实际改了哪些行（每条语句命中几行），计划 4 写计划时有过草稿，没有采用。全量时 2% 的误杀可以接受。
- **速度：** 1 票、3 并发时，墙钟约每票 3.8 秒（617 票用了 2357 秒），约每小时 950 票；思考被截断约 3.5%，重投解决。全量约 3,300 条过检查和预封顶，各 1 票，约 3.5 小时。
- **子查询偏高：** 新一批 15.9%，略超 15% 的目标。全量时用 `task_stats` 再看，超了就把 `SUBQUERY` 从 0.13 往下调。
