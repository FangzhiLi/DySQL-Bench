## 1. 实现了什么

代码在 `DySQL-Bench/dysql_bench/taskgen/`，命令行入口是 `scripts/taskgen.py`，每个步骤一个子命令，步骤之间只通过 JSONL 文件传递，按 id 断点续跑。

| 步骤 | 文件 | 做什么 |
|---|---|---|
| 锚点输入 | `db_select.py`、`scripts/select_dbs.py` | `candidate_anchors.json` 改成自包含：带 sqlite 路径、单列外键 `fks`、多列外键 `fks_composite` |
| 建树 | `trees.py` | 对每个人物锚点行，沿外键取子表行（两跳经中间表）、父表行；先用外键重算 scope 并与 JSON 核对，55 个库 197 个锚点全部一致 |
| schema | `schema.py` | DDL、BIRD 列说明、库描述（LLM 生成一次，缓存在 `docs/data_gen/db_descriptions.json`） |
| LLM 客户端 | `llm.py` | OpenAI 兼容接口，429/5xx 退避重试，兼容 GLM 的 `reasoning_content` 和 vLLM 0.30 的 `reasoning` |
| 出题 prompt | `prompt.py`、`examples.json` | 按比例抽任务类型、难度、形状；DySQL 的出题 prompt 加类型段、形状段；few-shot 手写 15 条 |
| 出题 | `generate.py` | 调 GLM-5.3，解析 `<answer>`；每条结果一返回就写盘；`--retry-errors` 重出 API 失败的候选 |
| 执行检查 | `check.py` | 在内存副本上执行 gold SQL：报错、0 行命中、单条超 50 行、写出 scope、字面量不在 instruction 里都拒；同时算出类型、难度、模板 |
| 校准 | `scripts/calibrate_check.py` | 在 DySQL 1062 条上跑执行检查：非第 7 类通过率 90%，去掉部分 no-op 后 95%，类型一致率 87%（`docs/data_gen/2026-09-28-check-calibration.md`） |
| 校验 | `verify.py` | 本地 Qwen3.8-27B-NVFP4 多数投票；每条投完就写盘；API 失败的票不计数、续跑时重投 |
| 去重 | `dedup.py` | 每人 ≤ 2、每模板 ≤ 15、每库 ≤ 600，稀有模板优先 |
| 输出 | `convert.py`、`envs/gen/` | `data/taskgen/<db>/tasks.jsonl` + `manifest.json`；通用 `GenEnv`，`run.py --env gen:<db> --task-split train` 直接评测 |
| 统计 | `stats.py` | 试点验收指标 |
| 部署 | `scripts/serve_verifier.sh`、`scripts/taskgen_pilot.sh` | 校验模型服务；一键跑一个库的全部步骤 |

### 和计划不一样的地方（全部决定）

每条都记了原因和做错的代价。

1. **多列外键单独列出**（Task 2）。professional_basketball、college_2 有 4 个锚点的父表只能经多列外键到达。scope 计算用它们，建树只 join 单列外键。代价：这两个库的树里没有 teams、section 的示例行。
2. **执行检查的 scope 放宽为"库内所有锚点 scope 的并集"**（Task 8）。设计 §7 写的是"该锚点的 scope"，但 DySQL 实测的性质是"某个锚点的 scope"：chinook、music 的客户会改全局歌单。代价：生成任务可能写说话人树之外的表，仍受字面量检查和校验约束。
3. **字面量检查接受 0/1/true/false、`%` 模式、英文日期写法、数字单词**（Task 8）。代价：依赖未说出的 0/1 的任务会漏过。
4. **"只有 no_write"的判定调整**（Task 7）。一条 0 行的 UPDATE 不再同时报两个原因。
5. **校验模型换 vLLM 版本**（Task 13）。NVIDIA 的 NVFP4 把 `lm_head` 也量化了，评测用的旧镜像（vLLM 0.19，2026-04）加载不了。按你的提示查了版本，改用 `vllm/vllm-openai:v0.30.0-aarch64`（cu130）。`-cu129` 那个 arm64 镜像本身 torch 和 torchvision 不匹配，不能用。评测镜像没动。
6. **出题并发 5**（你给的上限），**校验并发 32**（按你选的方案 2）。
7. **校验 prompt 重写**（Task 14，最重要的一条，见 §2.3）。
8. **试点第二轮只投 3 票**（原计划 5 票）。为了早上前跑完；所以这次没有测"3 票和 5 票的差别"。

## 2. 试点验收（beer_factory，100 条候选）

### 2.1 漏斗

| 步骤 | 条数 | 说明 |
|---|---|---|
| 候选 | 100 | 第一轮 12 条因 GLM 429 失败，用 `--retry-errors` 重出后补齐 |
| 解析失败 | 0 | |
| 执行检查通过 | 93 | 拒掉：SQL 报错 9，字面量缺失 1，没改任何行 1 |
| 校验通过（3 票多数） | 82 | 86% 的候选三票一致 |
| 去重后留下 | 82 | 样本小，封顶规则没有触发 |

执行检查拒掉的 9 条 SQL 报错有两类，都是 prompt 可以修的：
- 表名 `transaction` 是 SQLite 关键字，模型有时没加引号。
- 新插入行的 `TransactionID` 和已有 ID 重复。

### 2.2 分布和多样性

按执行检查算出的标签，93 条通过执行检查的候选：

| 指标 | 试点 | 目标或 DySQL 区间 |
|---|---|---|
| 类型 1 / 2 / 3 / 4 / 5 | 46 / 8 / 5 / 6 / 34 % | 46 / 12 / 5 / 8 / 29 % |
| 难度 简单 / 中等 / 困难 | 24 / 42 / 34 % | 26 / 45 / 29 % |
| 要求的类型和算出的类型不一致 | 0 条 | |
| 模板数 | 45 | DySQL 每库 9–76 |
| 最大模板占比 | 11% | DySQL 12–55% |
| 每人任务数 | 1.0 | DySQL 1.0–2.6 |
| 多条写语句 / 归属子查询 / 归档 / 改公共或他人数据 | 57 / 36 / 3 / 13 | 四种难题型都出现了 |

每一项都在验收线内：类型偏差都在 10 个百分点以内，没有第 7 类。归档题偏少（3 条），这是 beer_factory 的结构决定的，它没有天然的归档表。

### 2.3 校验：第一轮全拒，改 prompt 后正常

- **第一轮（DySQL 原校验 prompt + agent policy，5 票）拒掉了全部 93 条**：440 票 No，25 票解析失败。原因是校验模型把 gold SQL 当成 agent 的对话记录来审，因为里面没有"向用户确认""回答查询问题"这些对话步骤而判错，而这些步骤永远不可能出现在 SQL 列表里。第一轮的结果保存在 `results/taskgen/beer_factory/round1_policy_prompt/`。
- **第二轮改成只审 SQL 本身**：是否正确完整地实现了请求、有没有多改、参数是否都在请求里、看不到 SQL 的 agent 能否做到同样结果、SQL 是否合法。6 条抽查 5 条通过后全量重跑，82/93 通过。
- **单票就很稳定**：第一票和三票多数结论一致 89/93（96%）。
- **有 10% 的票解析失败**（29/279），计为 No。多半是模型没写规定的结尾行或输出被截断，没有细查。

### 2.4 人工抽查 20 条

从 82 条里按 seed 0 随机抽 20 条，由我（Claude）逐条读 instruction 和 SQL，不是由人核对，建议你自己也看几条。

- **20 条全部正确**，和校验结论 20/20 一致：参数都在 instruction 里，SQL 实现了请求，没有多改。
- **看到的弱点：**
  - 角色名重复。"Priya Raghavan"出现两次，"records coordinator"这个身份出现多次。
  - 开场套路重复。"moved across town"出现三次，"改之前先告诉我 X"很常见。
  - 简单题偏向改电话、改地址。
  - 第 4 类（替别人改数据）和 agent policy 的"只能帮一个用户"冲突。DySQL 自己也有这个冲突，是设计时有意保留的。

## 3. Qwen3-4B 在试点任务上的表现

82 条，每条 1 次，用户模拟器 Qwen2.5-72B-AWQ，并发 16，结果在 `results/taskgen/beer_factory/agent_4b/`。

| 分组 | 条数 | 通过率 |
|---|---|---|
| 全部 | 82 | **23.2%** |
| 简单 / 中等 / 困难 | 22 / 35 / 25 | 23 / 23 / 24 % |
| 类型 1 本人 | 40 | 22% |
| 类型 2 本人 + 公共 | 6 | 17% |
| 类型 3 只改公共 | 4 | 25% |
| 类型 4 替他人 | 6 | 0% |
| 类型 5 代办 | 26 | 31% |
| gold 写 1 / 2 / 3 条语句 | 33 / 43 / 6 | 18 / 26 / 33 % |

作为对照，4B 在 DySQL 上是 29.8%。

**怎么看：**
- **23% 落在 20–50% 的验收区间，适合做 GRPO 训练数据。** 太难会整组全错、没有梯度，太简单则学不到东西。
- **难度标签在 4B 身上没有区分度**，简单题和困难题都是 23% 左右。原因是 4B 的失败主要不是 SQL 写错，而是**根本没执行写操作**：抽看 5 条失败的简单题，4 条 agent 一条写语句都没发，另一条是大小写问题（写了 `'can'`，gold 是 `'Can'`）。整体"编造执行结果"比例 62%，和 DySQL 基线的问题一致。这正是训练要解决的。难度标签是按 DySQL 上 32B 和 4B 的通过率校出来的，等模型学会"真的去写"以后应该会重新拉开差距，训练时再看。
- **类型 4 是 0/6**：agent 多半按 policy 拒绝替别人改数据。样本很小，但要注意这一类可能在训练里给出互相矛盾的信号（见"需要你决定的事"）。

## 4. 代码审查

用一个独立的 Opus 子代理审查了整个分支。它发现的问题和处理如下。

**已修（1 个严重、7 个重要，每个都先写了失败的测试）：**
- 带行尾注释的 SQL 或 `BEGIN; ... COMMIT;` 会让执行检查崩溃，而且整库的检查结果一条都不写。已修，现在每条候选单独写盘。
- `WITH ...` 开头或以注释开头的写语句被当成只读。
- 出题要等整批结束才写盘，中途被杀就全丢。
- 模型返回的 JSON 里 instruction 不是字符串时会中断整批。
- 校验时 API 失败被记成一张永久的 No 票。
- 重复运行 `trees` 会多出树。
- `run.py` 不接受 `gen:<db>`。
- "归档"标签有误报。

**记下没修的小问题：**
- 字面量检查是子串匹配（`203` 能匹配 `2030`）。
- gold 里用 `CURRENT_TIMESTAMP` 能通过检查，但评测时永远对不上。
- 200 但没有 `choices` 的响应不会被 `--retry-errors` 重出。
- 没有读 `Retry-After`。
- 触发器 SQL 把表名放在字符串字面量里。
- 统计里"改公共表"的计数口径不对。
- 两个校验进程同时补票时可能丢记录。

## 6. 需要你决定的事

1. **校验怎么提速（必须）。** 17 天不可行。试点数据支持的做法：
   - **首选：先 1 票，只对 No 票补到 3 票。** 第一票和三票结论 96% 一致，92% 的候选第一票就是 Yes。这样平均约 1.15 票/条，全量约 6.5 天。
   - **再叠加：35B-A3B 做第一票。** 速度快 5–10 倍，全量可以压到 2–3 天。需要先用试点这 93 条对比它和 27B 的一致率，约 1 小时。
   - **可选：`reasoning_effort` 调低。** 能缩短思考长度，但对准确率的影响要测。
2. **第二轮 prompt 修改（我可以做）。** 修 `transaction` 关键字引号和新 ID 冲突两个问题：在数据块里给出每张表的下一个可用 ID，并要求所有表名加双引号。同时加入角色名和开场白的多样性要求。
3. **类型 4（替他人改数据）要不要保留。** 它和 agent policy 冲突，4B 在这类上是 0%。DySQL 评测集里有 5.4% 是这一类，保留能对齐评测；但训练时 agent 若按 policy 拒绝就拿 0 分，可能教它违反 policy。两个选择：保留并在 instruction 里给出明确授权（现在已经这样做了）；或者训练集去掉这一类。
4. **下一个库。** 按计划是 books（15 张表）。修完第 2 点就可以开始。
