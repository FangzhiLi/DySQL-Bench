# 32B / 4B / 1.7B 错因对比：大模型做对的，小模型为什么做不对

数据：三个 pass@1 全量跑（`DySQL-Bench/results/full_qwen3_{32b_think_on_c12,4b_think_on_c16,1.7b_think_on_c16}`），按 (env, task_id) 逐任务配对。
单模型的错因分布见 2026-09-17（32B）和 2026-09-19（4B/1.7B）两份报告，这里只回答"同一个任务，为什么 32B 对、小模型错"。
脚本：`scripts/classify_failures.py`（主因），`scripts/replay_intended_writes.py`（离线重放，见 §4）。下文"去 no-op"指去掉 gold 写 0 行的任务。

## 结论

1. **4B 与 32B 的差距几乎全是协议/格式问题，不是 SQL 能力问题。** 32B 对、4B 错的 277 个任务里，75% 是 4B 的写操作根本没进库（65% SQL 包在 `<action>` 等环境不认的标签里，10% 没写 SQL 就宣布完成）。4B 只要第一次用了可执行格式，同一批任务上它的通过率比 32B 还高（56.0% vs 48.9%）。
2. **1.7B 有两道坎：格式 + 多块 SQL，此外还有一部分真实能力差距。** 32B 对、1.7B 错的 379 个任务里，67% 是格式（SQL 包在 `<result>` 里或没写 SQL），20% 是一条消息写多个 SQL 块、后面的写被丢弃。1.7B 即使格式对，同一批任务上也只有 29.0%（32B 46.9%）。
3. **格式错误的根源在 system prompt + user sim。** prompt 只说"write the SQL in a code block"，没写 ```` ```sql ````，全文唯一出现的标签是 `<result>`（用来描述执行结果）。1.7B 就拿 `<result>` 包 SQL，4B 自造 `<action>`。包错之后环境把它当成对用户的回复，user sim 会顺着演（"your birthplace has been updated"），模型收不到"没执行"的信号，所以**格式在第一条 SQL 时就定型，几乎从不自我纠正**（4B：463 个包错开局的 run 只有 3 个后来改对）。
4. **离线重放（§4）量化了这一点**：把每个模型写下的全部写语句都执行，32B / 4B / 1.7B 分别从 46.7 / 30.0 / 16.2 升到 56.5 / 54.5 / 45.6。4B 与 32B 的差距有 88% 来自协议问题，1.7B 有 64%。
5. 反方向也存在：4B 对、32B 错的有 104 个任务，主因是 32B 的多块 SQL（37 个）。32B 更"能干"，但更不守"一次只执行一条 SQL"的规则。

## 1. 配对总览

三个模型（去掉 traj_lost 后 1062 个任务全部可配对）的通过模式 (32B, 4B, 1.7B)：

| 模式 | 任务数 |

| 只有 32B 对 (1,0,0) | 224 |
| 32B+4B 对 (1,1,0) | 155 |

单 trial 噪声很大：大量任务只被一个模型做对，32B 490 个通过任务里只有 58 个三个模型都过。所以下文只看比例和成因，不看个别任务。

## 2. 32B 对、小模型错：小模型的主因

| 小模型主因 | 32B✓ 4B✗（277） | 32B✓ 1.7B✗（379） |
|---|---|---|
| C. SQL 包在不可执行的标签里（phantom） | **65.0%** | **59.6%** |
| C. 没写 SQL 就宣称完成 | 10.1% | 7.4% |
| B. 多个 SQL 块，后面的写被丢 | 4.7% | **20.3%** |
| F. 值 / WHERE 写错（含编造 ID） | 9.4% | 3.4% |
| A. 异常终止（thinking 耗尽 / 超长 / 步数） | 5.8% | 5.0% |
| D. 漏写一部分 | 1.4% | 2.4% |
| E. 多改了表 | 1.8% | 0 |
| G. gold no-op 被写坏 | 1.4% | 1.6% |

真正属于"SQL 写错"的（D+E+F）在 4B 只有 13%，1.7B 只有 6%。

## 3. 跨过格式这道坎之后

按每个 run 第一条 SQL 的格式分组（去 no-op）：

| | 4B | 1.7B |
|---|---|---|
| 开局就用可执行格式的任务数 | 468 | 407 |
| 该组小模型通过率 | **56.0%** | 29.0% |
| 同一批任务 32B 通过率 | 48.9% | 46.9% |
| 开局包错的任务上 32B 通过率（难度对照） | 44.5% | 45.2% |

开局包错的任务对 32B 也只是略难一点，说明包不包错基本不取决于任务难度（各库占比 29%～77%，也没有特别集中）。

开局格式正确的 run 里的行为对比（去 no-op）：

| | 32B | 4B | 1.7B |
|---|---|---|---|
| n | 918 | 472 | 422 |
| 通过率 | 47.8% | 55.7% | 28.2% |
| 有多块 SQL 的 run | 36.1% | **19.5%** | **58.8%** |
| 有编造 `<result>` 的 run | 66.0% | 36.2% | 66.6% |
| 第一次写之前的 SELECT 次数 | 2.22 | 1.80 | 1.91 |
| 写之前征得用户确认 | 45.7% | 57.9% | 32.8% |
| 有 SQL 报错的 run | 8.9% | 10.4% | 20.9% |
| 有写 0 行的 run | 8.1% | 5.7% | 9.0% |
| thinking 耗尽 | 0.1% | 1.5% | 1.2% |

- 4B 在格式对的时候是三者里最守规矩的：多块少、编造少、确认多。这就是它在同一批任务上反超 32B 的原因，也对应了 32B 在"4B 对、32B 错"任务上的主因（多块 SQL）。
- 1.7B 格式对了之后仍然有三类真实问题：一半以上的 run 一条消息塞多个 SQL 块；SQL 报错率是另两个模型的两倍；很少先确认再写。

## 4. 离线重放：如果写下来的 SQL 都被执行了

`scripts/replay_intended_writes.py`：不调用任何模型。对每个 run，从 agent 消息里按顺序抽出所有 UPDATE/INSERT/DELETE，不管包在什么标签里（```` ```sql ````、`<action>`、`<result>`、`<query>`，以及被丢弃的额外块），完全相同的语句只执行一次，在干净的库副本上执行，然后用环境自己的整库 hash 和 gold 比较。输出：`DySQL-Bench/results/replay/replay_3models.json`。

校验：executed 模式（只重放 sql_log 里真正执行过的语句）和原始 reward 一致 1048/1050（32B）、1049/1056（4B）、1045/1059（1.7B）。少数不一致来自重放时逐条执行和原 run 按块执行的回滚差异。人工抽查 1.7B 的 4 个"重放后通过"任务，SQL 都和 gold 等价，只是包在了 `<result>` 里。

| | 32B | 4B | 1.7B |
|---|---|---|---|
| 原始 pass^1 | 46.7% | 30.0% | 16.2% |
| **重放全部写下的写语句** | **56.5%** | **54.5%** | **45.6%** |
| 去 no-op：原始 → 重放 | 46.2 → 57.1 | 28.4 → 54.1 | 13.4 → 45.4 |
| 因重放多过的 / 少过的 | +116 / −13 | +271 / −13 | +325 / −14 |
| 开局格式正确的 run：原始 → 重放 | 48.3 → 57.8（n=1009） | 55.2 → 61.4（n=518） | 30.0 → 45.3（n=466） |
| 开局就包错的 run：原始 → 重放 | —（n=7） | 6.7 → 51.7（n=466） | 5.5 → 45.6（n=546） |

差距分解（以 32B 为基准）：

| | 实测差距 | 重放后差距 | 协议问题能解释的比例 |
|---|---|---|---|
| 4B | 16.7 pt | 2.0 pt | **88%** |
| 1.7B | 30.5 pt | 10.9 pt | **64%** |

- 32B 自己也有 10 个点被协议问题吃掉（主要是多块 SQL 被丢），与 2026-09-17 的归因一致。
- 4B 的 SQL 内容几乎和 32B 一样好，差距基本都是格式问题。
- 1.7B 在格式和多块问题之外，还有约 11 个点的真实差距（值写错、漏写、SQL 报错），这部分才是要靠能力训练来补的。
- 重放为什么能这么高：很多任务的指令本身就给出了全部 ID 和新值（例如 "rental ID 10296 with payment ID 15357, delete both"），不查库也能写对。这是 benchmark 的特性，也意味着 DySQL-Bench 对"根据查询结果决策"的考察比看上去弱。
- 这是估计值，不是重跑：包错格式的 run 里模型没看到真实结果，对话走向也会不同；重放既可能高估（真实执行后模型可能又做了多余的写），也可能低估（看到结果后本可以修正）。

## 5. 对训练的含义

- 对 4B 来说，格式对齐（SFT/RFT warm-start 或格式奖励）几乎就能拿回全部差距；GRPO 的重点应该放在格式和"一次一条 SQL"上，而不是 SQL 生成能力。
- 1.7B 除了格式，还要单独压多块 SQL；SQL 正确率（报错率 2×）也是真实短板。
- 评测侧：system prompt 的格式说明有歧义（没写 ```` ```sql ````，只出现 `<result>` 标签），user sim 会替没执行的 SQL 圆场。这两点会系统性地低估小模型。报告小模型结果时，应注明这是在这套 prompt 下的格式失败；是否另做一个"prompt 明确格式"的对照 run，需要决定。
