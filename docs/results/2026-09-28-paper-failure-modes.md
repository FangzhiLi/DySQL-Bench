# DySQL-Bench 论文列出的失败模式 —— 在我们三个 baseline 上的实测

论文：arXiv 2510.26495v2，§VI-C～F。数据：`DySQL-Bench/results/full_qwen3_{32b_think_on_c12,4b_think_on_c16,1.7b_think_on_c16}`（去掉 traj_lost 后 n = 1050 / 1056 / 1059）。
脚本：`DySQL-Bench/scripts/paper_failure_modes.py <run_dir> ...`（按 run 打标签，一个 run 可以有多个标签；列出发生率、有/无该标签时的通过率、在失败里的占比）。

## 论文自己的失败归因（摘要）

| 论文章节 | 论文结论 | 是否量化 |
|---|---|---|
| VI-C | Pass^k 随 k 明显下降，多轮交互不稳定 | 是（我们只跑了 1 个 trial，无法对照） |
| VI-D | 外在幻觉：SQL 块后紧跟自写 `<result>`，编造结果。DeepSeek-V3 44.28%，OmniSQL-32B 26.15%，GPT-4o 0.09%。归因于后训练的逐步推理习惯（未验证） | 是，只有发生率，没有对通过率的影响 |

## 1. 编造 `<result>`（VI-D）

| | 32B | 4B | 1.7B |
|---|---|---|---|
| 论文定义（SQL 块后紧跟 `<result>`）发生率 | **57.7%** | 14.8% | 15.8% |
| 任意位置出现编造的数据型 `<result>` | 66.8% | 50.7% | 35.6% |
| 编造的查询结果和真实结果对不上的消息占比 | 77% | 84% | 94% |
| 把编造出来的数字写进了库（该数字未出现在任何真实结果或用户消息里） | 12.0% of runs，通过率 22.2%，占失败 **17.5%** | 2.7%，占失败 3.1% | 2.0%，占失败 1.9% |
| 论文定义的编造中，同一条消息里还有额外 SQL 块的比例 | 54% | 38% | 52% |
| 编造了但没有额外 SQL 块 → 通过率 | 58% | 64% | 55% |
| `<result>` 被当成 SQL 包装（格式错误，不是幻觉） | 1.4% | 4.4% | **57.7%**，占失败 63.9% |

结论：
- 按论文的定义，32B 的编造率（57.7%）比论文里最差的 DeepSeek-V3（44.28%）还高。而且编造的值几乎都是错的，不是"猜对了"。
- **但编造本身大多不致命**：环境下一轮会返回真实结果，模型通常会改用真实值。不带额外 SQL 块的编造 run，通过率反而高于整体。
- 致命的是两种组合：(a) 编造结果 + 同一条消息里的后续写操作被丢弃（即 2026-09-17 归因里的主因 B，占 32B 失败 39%）；(b) 编造的 ID/数值被真的写进库（占 32B 失败 17.5%，Fig.10 就是这一类）。
- 小模型的 `<result>` 问题主要是格式错误（1.7B 把 SQL 包在 `<result>` 里）。论文的定义捕捉不到这一类，这一类也不应该算作幻觉。
- 4B 和 1.7B 上"有编造的 run 通过率更高"是混杂因素：用了正确 ```sql 块的 run 才有机会出现这种模式，而格式正确才是小模型能否通过的主因。

## 2. 复读循环（VI-F a）

| | 32B | 4B | 1.7B |
|---|---|---|---|
| 单条消息内同一行（≥40 字符）重复 ≥3 次 | 1.2% | 0.7% | 1.2% |
| 连续 3 条 assistant 消息完全相同 | 1.0% | 1.4% | 3.0% |
| 异常终止（max_steps / context_overflow / length_no_content） | 1.3% | 4.7%（其中 thinking 耗尽 3.6%） | 4.9% |

结论：确实存在，但只占失败的 1～5%，不是主要失败原因。4B 相关的问题是 thinking 预算耗尽，不是复读。

## 3. 放弃任务 / 死守验证规则（VI-F b）

gold 有写操作，但 agent 一次写都没执行，且出现拒绝或转人工的措辞：

| | 32B | 4B | 1.7B |
|---|---|---|---|
| 转人工（escalate） | 4.5%，占失败 7.7% | 0.4% | 0.3% |
| 拒绝措辞（unable to verify/proceed…） | 2.4% | 1.0% | 3.0% |
| 其中与身份验证有关 | 2.8%，占失败 **4.8%** | 0.6% | 1.5% |

典型样例（32B，eu_soccer 163）："no user table exists in the provided database schema. Cannot authenticate … Transferring to human agent"。eu_soccer 里没有用户表，模型照搬 system prompt 里"先验证身份"的规则，于是卡住。和论文 Fig.12 是同一类问题。

## 4. SQL 报错与对话长度（VI-E）

| | 32B | 4B | 1.7B |
|---|---|---|---|
| 0 次 SQL 报错的 run 占比 | 91.4% | 95.1% | 90.6% |
| 0 次报错 run 的通过率 | 48.5% | 29.4% | 16.7% |
| agent tokens 中位数 通过 / 失败 | 3754 / 4857 | 4169 / 4554 | 3508 / 3722 |
| agent tokens 最大值（失败） | 45292 | 23082 | 42184 |

结论和论文一致：SQL 能执行、不报错不是瓶颈，九成以上 run 零报错，但通过率仍然很低。失败的 run 更长，也有长尾。

## 5. 论文没覆盖、但在我们数据里是主因的

- 32B：一条消息里写多个 SQL 块，环境只执行第一块，后面的写操作被丢弃（占失败 39%）。论文把这种现象的表层症状（自写 `<result>`）归为幻觉，但真正导致失败的是后面的写操作被丢弃这一协议违规。
- 4B / 1.7B：SQL 放在不可执行的包装里（4B 用 `<action>`，1.7B 用 `<result>`），占小模型失败的 56%。
- gold 自身是 no-op（3.8%，见 2026-09-17 报告）。

## 对奖励设计的含义

与 2026-09-19 的排序一致，只是把论文的幻觉拆开来看：
1. 格式：SQL 必须放在可执行的块里（小模型的主因）
2. 每轮只写一个 SQL 块，写完就停，等环境返回（32B 的主因；同时能消掉大部分论文定义的"幻觉"）
3. 惩罚写入库的值无依据（编造值流入写操作，32B 失败的 17.5%）。单纯惩罚出现 `<result>` 标签的收益有限
4. thinking / 步数预算（4B 的 length_no_content、复读）
5. 身份验证的灵活处理：数据库里没有用户表或用户提供替代标识时不要卡死（32B 失败的约 5%）。在任务生成里，应确保"验证身份"与 DB 结构匹配
