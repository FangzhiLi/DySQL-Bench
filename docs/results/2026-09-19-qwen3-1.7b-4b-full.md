## Why they fail

Failure classifier `scripts/classify_failures.py`, primary cause per failed run (top-level class):

| class | 32B-AWQ (572 fails) | 4B (745 fails) | 1.7B (890 fails) |
|---|---|---|---|
| A. abnormal termination (ctx overflow / thinking exhausted / max steps) | 4.5 % | 7.4 % | 6.1 % |
| **B. write dropped: ≥2 SQL blocks in one turn, env runs only the first** | **39.0 %** | 7.7 % | 20.6 % |
| **C. no write reached the DB** | 13.5 % | **65.5 %** | **64.5 %** |
| — of which: SQL emitted in a non-executable wrapper | 2.1 % | 56.4 % | 56.4 % |
| — of which: claimed done without any SQL | 4.5 % | 7.7 % | 7.5 % |
| — of which: escalated to human | 6.5 % | 0.1 % | 0.1 % |
| D. partial: some writes, one sub-request skipped / wrong table / SQL error unrecovered | 11.2 % | 3.5 % | 3.4 % |
| E. wrote an extra table | 4.2 % | 1.7 % | 0.1 % |
| F. wrong values / wrong WHERE (incl. hallucinated IDs) | 23.8 % | 12.2 % | 3.9 % |
| G. gold no-op task the agent broke by writing | 3.8 % | 2.0 % | 1.5 % |

Read down the columns: the 32B fails *after* getting its SQL executed (B, D, F = 74 %); the small models fail *before* (C = 65 %).

### The dominant failure is format, not SQL

The harness executes SQL only from a ` ```sql ` fence or `<sql>…</sql>`; the prompt says only "write the SQL in a code block".

| | 32B-AWQ | 4B | 1.7B |
|---|---|---|---|
| assistant turns with executable SQL | 56 % | 31 % | 34 % |
| assistant turns with SQL inside a wrapper the env ignores | 1 % | **29 %** | **36 %** |
| the wrappers used (turn counts) | `<result>` 71 | `<action>` 2048, `<result>` 1090, `<query>` 109 | `<result>` 2404, `<query>` 12 |
| runs where **no** write was ever executed (`no_write_executed`) | 12 % | **53 %** | **64 %** |
| runs with a fabricated `<result>` after own SQL | 66 % | 52 % | 83 % |
| runs with ≥2 SQL blocks in one turn | 34 % | 10 % | 27 % |

- **4B** invents an `<action>…</action>` protocol (2048 turns) and never gets feedback that nothing ran. It is otherwise the more
  disciplined model: few multi-block turns (10 %), few max_steps (4). Its distinctive failure is **thinking exhaustion**: 38 runs
  (5.1 % of fails) spent all 8192 tokens in reasoning and emitted no answer, 7× the 32B rate.
- **1.7B** wraps SQL in `<result>` (2404 turns), i.e. it confuses the tag the prompt uses for *execution output* with the call format.
  It also inherits the 32B's multi-block habit (27 % of runs, 216 dropped writes) and is the most verbose: 26 max_steps, 19 context
  overflows, and the highest fabrication rate (83 %).
- Fabricating a `<result>` costs everyone: pass rate with vs without fabrication is 36/65 (32B), 21/40 (4B), 12/34 (1.7B).

The 9 `context_overflow` runs whose traceback is in `user.py` (3 in 1.7B, 6 in 4B) are the **user simulator's** 16k context overflowing
on a long agent-generated conversation, reclassified from `error` by `scripts/reclassify_errors.py` (same treatment as the 32B run).

## Ops

- Three vLLM engines on one 121 GB unified-memory GB10: user sim 0.50 / 1.7B 0.10 / 4B 0.15; idle `free -g` available 26 GB,
  21–26 GB at every check during the runs. Engine stats over the whole run (vLLM 10 s samples):

  | engine | max running | samples with a queue | max queued | samples with KV ≥ 95 % |
  |---|---|---|---|---|
  | user sim (max-num-seqs 32, KV 53k tok) | 27 | 0.1 % | 3 | 0 |
  | 4B agent (0.15, KV 69k tok) | 16 | 0.0 % | 1 | 0.1 % |
  | 1.7B agent (0.10, KV 58k tok) | 16 | **5.7 %** | **11** | **3.0 %** |

  The 1.7B agent's KV budget was tight: it is the more verbose model (19 context overflows up to 40k tokens), and 16 concurrent
  long contexts filled 58k tokens. No errors resulted (vLLM v1 queues/recomputes), but give it ≥ 0.15 next time. User sim at
  max-num-seqs 32 was sufficient for two c=16 runs.
- Throughput: 1.7B 49 tasks/h, 4B 42 tasks/h at c=16 (eu_soccer at c=8: 28 tasks/h). The two runs together took 25.3 h wall versus
  28.3 h for the single 32B run; agents share the memory bus with the 72B user sim, so per-request decode was 8–14 tok/s.
- Pilot's estimate (0–10 % pass) was badly low: the 10 pagila tasks it used were an unlucky sample of a hard env. Pilot did correctly
  predict the dominant failure mode and the thinking on/off decision.
- ~50 leaked sqlite scratch dirs (~1 GB) from abnormal terminations; cleaned after the runs.

## Implications for step 4 (GRPO)

1. **Format compliance is the first reward term**, and probably an SFT/RFT warm-start target before GRPO: 56 % of both small models'
   failures are SQL that never reached the database. A format reward alone cannot exceed ~29 % (4B) / ~16 % (1.7B) → the ceiling
   after fixing format is bounded by what the executed-SQL runs achieve, which the 32B column suggests is 45–60 %.
2. **"One SQL block per turn, then stop"** is the second term; it is the 32B's #1 failure and the 1.7B's #2.
3. **Fabricated `<result>` should be penalised directly**: it is observable in the trajectory and halves the pass rate for every model.
4. For 4B specifically, a **thinking-length budget** matters (38 exhausted runs); for 1.7B, **step and context budgets** matter more.
5. A **format-tolerant parser ablation** (accept `<action>`, `<result>`-wrapped SQL, bare fences) on the same trajectories would
   measure how much SQL skill hides behind the format wall, at zero re-run cost. Separate tag; not a baseline change.
